# «Бункер / Последний вагон» V2 — связная игра

Дата: 21 августа 2026  
Статус: письменная спецификация на проверке пользователя  
Выбранный подход: фундамент №2 — сохранить устойчивое ядро и заменить старый игровой слой

## 1. Решение

Сохраняем уже работающие регистрацию, реальные имена гостей, устройства, вагоны, TV-защиту, Realtime, серверные таймеры, инвентарь, архив, персонажей и репетиционный сброс. Поверх них строим один связный сценарий:

`Подготовка → Роли → M01 → Пауза → M02 → M03 → M04 → M05 → M06 → Неизвестный пассажир → Пауза → Финал 30:00 → Бункер открыт → Завершено`.

Старые `mission_a` и `mission_b` больше не являются игровой логикой V2. Они остаются только для чтения уже существующего legacy-run до его завершения или сброса. V2 не пишет в них и не выводит их названия игрокам.

Эта спецификация заменяет игровой сценарий из `2026-08-19-bunker-quest-design.md` и уточняет фундамент из `2026-08-20-adaptive-bunker-game-design.md`. Стабильные свадебные модули вне Бункера не перерабатываются.

## 2. Цели и критерий готовности

Готовая игра должна:

- работать для 15–40 зарегистрированных гостей и 2–5 активных вагонов;
- использовать только реальные имена из регистрации;
- дать каждому гостю одну понятную роль и одну ситуационную способность;
- связывать последствия каждой миссии со следующими миссиями и финалом;
- показывать на телефоне только актуальную задачу и доступные действия;
- показывать на TV общий драматический момент, а не телефонную форму;
- давать ведущему понятный русский пульт, таймлайн и безопасные ручные fallback-команды;
- восстанавливаться после reload, потери Realtime и переподключения;
- позволять прогнать весь сценарий тестовыми гостями без записи мусора в production-run;
- не раскрывать правильные ответы, скрытые свойства и чужие персональные подсказки раньше времени.

Игра считается реализованной только после автоматического прогона размеров 15, 16, 17, 23, 32, 39 и 40, случайного end-to-end прогона каждого N от 15 до 40 и ручной проверки телефона 390×844 и TV 1920×1080.

## 3. Неприкосновенный фундамент

Единственные источники истины:

- `events` — событие и владелец;
- `guests` и device binding — реальный гость и его устройство;
- `carriages` и `guests.carriage_id` — состав вагонов;
- `bunker_state` — текущий run и глобальная стадия;
- `bunker_game_runs` — неизменяемый план конкретного запуска;
- серверное время — все дедлайны и 30-минутный финал;
- существующий refresh-only Realtime плюс polling/focus/online fallback;
- `BunkerScreenGuard` — самый высокий приоритет на общем экране;
- существующая owner-админка — единственный пульт ведущего.

Нельзя создавать вторую регистрацию, второй список вагонов, второй таймер, отдельный аккаунт Бункера или клиентский источник authoritative-состояния.

## 4. Масштабирование 15–40

Рекомендуемое число вагонов фиксируется при подготовке run:

| Гостей | Вагонов | Ожидаемый размер команды |
|---:|---:|---:|
| 15–18 | 2 | 7–9 |
| 19–26 | 3 | 6–9 |
| 27–36 | 4 | 6–9 |
| 37–40 | 5 | 7–8 |

Ведущий может выбрать 2–5 вагонов вручную, но система показывает предупреждение, если хотя бы в одном вагоне меньше трёх гостей или разница размеров превышает одного человека. Подтверждение атомарно распределяет текущих гостей и сохраняет snapshot. Поздний гость попадает в наименее заполненный вагон и не меняет уже принятые решения.

Все планы строятся по фактическим `activeWagonIds`, а не по жёстким `wagon_1 … wagon_5`.

### 5.1 Controlled random

Минимальное покрытие:

- technical: `power_engineer`, `electrician`, `mechanic`, `military_engineer`;
- medical: `surgeon`, `paramedic`;
- information: `cybersecurity_specialist`, `programmer`, `student`;
- communication: `signal_operator`, `radio_amateur`, `diplomat`, `psychologist`;
- bunker: `unemployed` или другой профиль с каноническим тегом `bunker`;
- navigation: `geologist`, `cartographer`, `train_driver`, `driver`;
- analytical: `cartographer`, `cybersecurity_specialist`, `lawyer`, `journalist`, `teacher`, `astronomer`.

Целевые минимумы:

| Гостей | technical | medical | information | communication | analytical | bunker | navigation |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 15–18 | 2 | 1 | 1 | 2 | 2 | 1 | 1 |
| 19–20 | 2 | 2 | 1 | 2 | 2 | 1 | 1 |
| 21–29 | 3 | 2 | 2 | 3 | 3 | 2 | 2 |
| 30–35 | ровно N уникальных профилей; минимумы не ниже диапазона 21–29 |  |  |  |  |  |  |
| 36 | все 36 уникальных профилей |  |  |  |  |  |  |
| 37–40 | все 36 профилей + N−36 контролируемых повторных выдач |  |  |  |  |  |  |

Один профиль может закрывать несколько категорий, но распределитель сначала использует разные профили. Для 30–35 выбираются N уникальных профилей, для 36 — весь каталог. Для N=37–40 допускается суммарно N−36 повторных выдач: повторяются 1–4 разных профиля по одному дополнительному разу, частота каждого profile key не превышает двух. Повторы разносит по разным вагонам и не создаёт два одинаковых профиля в одном вагоне, если существует другая допустимая раскладка.

Это осознанное исключение, необходимое для одновременно утверждённых требований «ровно предоставленные 36 профилей» и «игра работает до 40 гостей». Оно вступает в силу только после письменного утверждения этой спецификации пользователем. Новые профессии, имена, свойства и способности автоматически не сочиняются.

Распределение seed-детерминированное от `run_nonce`. Профиль сохраняется snapshot-ом с `profile_version`; изменение каталога не меняет уже запущенную игру.

### 5.2 Способности

У игрока одна способность. В V2 каждая способность имеет `maxUses=1`; увеличить до двух можно только отдельным утверждённым правилом миссии. Игрок не угадывает момент применения: сервер создаёт персональное доступное действие, телефон показывает понятное уведомление, а RPC атомарно проверяет миссию, владельца, остаток, применяет эффект и пишет событие.

Скрытое свойство не отправляется клиенту до reveal. `excluded` относится только к сюжетному персонажу; реальный гость продолжает участвовать.

## 6. Единый серверный автомат

Канонические состояния:

```text
LOBBY
CHARACTERS_READY
MISSION_01
BREAK
MISSION_02
MISSION_03
MISSION_04
MISSION_05
MISSION_06
UNKNOWN_PASSENGER
BREAK_BEFORE_FINAL
FINAL_30
BUNKER_OPEN
FINISHED
```

`STORY_BUNKER` остаётся только состоянием `contract_version=1`. Первая V2 forward-only migration ставит transitional check-constraint, допускающий одновременно `STORY_BUNKER` и `UNKNOWN_PASSENGER`, и создаёт отдельный V2 transition `MISSION_06 → UNKNOWN_PASSENGER → BREAK_BEFORE_FINAL`; V1/V2 RPC дополнительно валидируют состояние по `contract_version`. `STORY_BUNKER` удаляется из DB constraint только после доказанного отсутствия V1 runs. V2-клиенты и V2-RPC не вызывают legacy `owner_advance_bunker_game_state`. Никакой живой legacy-run не переписывается. В V2 UI и новых данных используется только `UNKNOWN_PASSENGER`.

Инварианты:

1. У run ровно одно текущее состояние.
2. Разрешён переход только в следующее состояние или идемпотентный повтор текущего.
3. Ведущий запускает каждый сюжетный этап вручную; сервер не перескакивает этапы по таймеру.
4. Завершение миссии открывает кнопку следующего этапа, но не нажимает её.
5. Любой дедлайн вычисляется от серверного `started_at`.
6. Любая необратимая команда имеет `command_id` и повтор возвращает исход первого выполнения.
7. Поздний гость получает роль текущего run, но не меняет frozen plan, квоты и уже зафиксированные исходы.

V2 не вызывает существующий `_refresh_bunker_run_guest_plan`. Каждый гость, зарегистрированный после создания V2 plan, независимо от текущей стадии получает `character_status='saved'` и `m01_eligibility='late_joiner'`: он никогда не входит во frozen M01 members/quota, даже если M01 ещё идёт. Гость может участвовать и применять способность только в ещё не завершённых событиях, но не добавляется задним числом в M04 required members/operators, M06 required voters или расчёт уже заработанных бонусов.

## 7. Контракт данных V2

Сохраняются и расширяются `bunker_guest_profiles`, `bunker_wagon_state`, `bunker_inventory_lots`, `bunker_archive_entries`, `bunker_game_events`.

Добавляются нормализованные проекции:

| Проекция | Назначение |
|---|---|
| `bunker_mission_instances` | экземпляр M01–M06, Unknown Passenger или Final для wagon/group/global scope |
| `bunker_mission_members` | участники вагона/группы, капитан, оператор, лимиты и локальный статус |
| `bunker_mission_decisions` | подтверждённые ответы, выборы и голоса |
| `bunker_ability_uses` | доказательство атомарного применения способности |
| `bunker_inventory_transfers` | предложение и атомарный обмен между вагонами |
| `bunker_archive_entitlements` | неизменяемый artifact плюс право вагона видеть/передавать улику и история provenance |
| `bunker_final_parameters` | coordinates, sector, access_code, gate_time, password |
| `bunker_command_receipts` | идемпотентность команды и сохранённый результат |

`bunker_game_runs.plan` получает `contractVersion=2`, `planVersion`, активные вагоны, snapshot размеров, M01 quota, M04 groups/operators, M05 route scenarios, M06 fragments и распределение финальных параметров. После запуска plan не меняется.

`bunker_game_events` — append-only журнал с `sequence`, `command_id`, `instance_id`, actor, correlation id и schema version. Он нужен для аудита и статистики, но текущий UI читает нормализованную проекцию, а не пересобирает всё состояние из лога.

Инвентарь ведётся как ledger. Расход и передача ссылаются на source lot, доступное количество никогда не отрицательное. Передача архивной улики не меняет исходную запись: accept блокирует source entitlement и создаёт destination entitlement с тем же immutable artifact и новым owner scope.

## 8. Командный API

Гостевой transport:

`submit_bunker_command(event_slug, device_key, command_id, command_type, payload)`.

Сервер сам определяет event, run, guest, carriage и role. Клиент не передаёт authoritative `guest_id`, `carriage_id`, `run_nonce`, цену сделки, правильный ответ или outcome.

Типы команд: `mission_confirm`, `submit_answer`, `use_ability`, `send_message`, `propose_trade`, `respond_trade`, `cast_vote`, `reveal_fragment`, `request_access`.

Owner-команды: `owner_prepare`, `owner_distribute`, `owner_transition`, `owner_hint`, `owner_extend_final`, `owner_force_outcome`, `owner_reset_run`. Необратимые и аварийные команды требуют причины и пишутся в журнал.

Уникальный ключ receipt: `(run_nonce, actor_kind, actor_id, command_id)`. `request_hash` хранится колонкой для сравнения. Повтор с тем же hash возвращает сохранённый result; тот же ключ с другим payload возвращает `idempotency_conflict`. Для owner `actor_id=auth.uid()`, для гостя — server-resolved `guest_id`.

Порядок блокировок: global state → mission instance → member/decision → profile/ability → inventory lot → final parameter → receipt/event.

## 9. Связный сюжет и последствия

Каждый `bunker_mission_instance.definition.presentation` — immutable snapshot. Он содержит `titleRu`, `objective`, `question`, `answerMode`, `options`, `deadlineSeconds`, `confirmCopy`, `successCopy`, `failureCopy`, `timeoutCopy`, `media`, `mediaAlt`, `publicTvSummary`, `privatePhoneDetail` и `primaryCta`. Полные экранные тексты берутся без переписывания из утверждённых пользовательских сценариев заданий 01–06, Unknown Passenger и Final; answer key хранится отдельно и никогда не входит в guest/TV read-model.

| Сцена | Главная задача/формат | Server deadline | Основной CTA | Timeout outcome |
|---|---|---:|---|---|
| M01 | выбрать quota персонажей, multi-select | 240 s | «Подтвердить решение» | ожидание owner assistance; автоматического выбора нет |
| M02 | ответить на 3 вопроса по 6 уликам | 300 s | «Отправить версию» | incomplete archive + продолжение сюжета |
| M03 | капитан распределяет до 3 решений из 5 | 360 s | «Подтвердить распределение» | невыбранные проблемы получают заявленные последствия |
| M04 | сообщения ≤120 символов, обмен и общий ответ | 300 s | «Передать» / «Подтвердить ответ» | channel overloaded + owner assistance outcome |
| M05 | необратимый выбор A/B | 90 s | «Подтвердить маршрут» | server выбирает безопасный B и маркирует timeout |
| M06 | голоса A/B/C и consensus | 480 s | «Подтвердить маршрут» | assistance +120 s, затем принудительный сюжетный fallback без coordination bonus |
| Unknown Passenger | сюжетное сравнение/персональная память | без общего таймера; 60 s action window после 84% | «Сравнить данные» / «Сообщить команде» | фиксируется отсутствие доступной связи, сцена завершается |
| Final | восстановить пять параметров | 1800 s + bounded bonus | «Запросить доступ» | терминал остаётся активным; owner emergency path доступен |

Authoring limits для телефона измеряются в эталонном `QuestionLayout` шириной 390 px: `titleRu` обязан занимать не более двух строк; основной `question` — одновременно не более 240 символов и не более четырёх отрендеренных строк. Не прошедший лимит текст делится: короткая формулировка остаётся в `question`, остаток переносится в `privatePhoneDetail` и открывается по «Подробнее» без сокрытия основного вопроса.

### M01 — «Лишний пассажир»

- Scope: один экземпляр на вагон.
- Система раскрывает предназначенную для M01 часть досье и просит команду выбрать требуемое число сюжетных персонажей.
- Quota: 0 для пустого вагона, 3 при 10+ гостях, 2 при 7–9, иначе 1.
- Один подтверждённый список переводит выбранных персонажей в `excluded`, остальных — в `saved`, раскрывает скрытые свойства и фиксирует доступные способности.
- Нет «правильного» человека и нет исключения реального гостя.
- Выбор влияет на набор ролей, подсказок и способов избежать потерь в M02–Final.
- Повтор подтверждения возвращает исход; изменить список после подтверждения может только owner override с причиной.

### M02 — «Чёрный ящик»

- Scope: вагон.
- Вагон исследует повреждённый бортовой регистратор; правильный ответ проверяется только сервером.
- Две обычные попытки. `system_access` или `terminal_hack` может дать дополнительную попытку/подсказку в рамках конкретного instance.
- Успех создаёт архивную улику `BK-17`; неуспех сохраняет неполный фрагмент, поэтому сюжет не блокируется.
- `BK-17` становится узнаваемым в событии «Неизвестный пассажир» и одним из источников финального параметра.

### M03 — «Аварийный запас»

- Scope: вагон; сервер назначает одного капитана из frozen snapshot.
- Вагон получает пять проблем и может закрыть не более трёх ресурсами или подходящими способностями.
- Инвентарь показывает реальные предметы: аптечка, рация, генератор, инструменты, запас воды, противогаз.
- Подтверждение одной транзакцией блокирует состояние вагона и lots, применяет способность, списывает предметы, фиксирует последствия и событие.
- Владелец подходящей способности сначала создаёт idempotent `pending_ability_commitment(instance_id, problem_key)`. Капитан видит только подтверждённое предложение и при финальном confirm атомарно принимает commitment, списывает способность и занимает один из трёх problem slots. Капитан никогда не применяет способность от имени другого гостя; отклонённый/истёкший commitment не списывает использование.
- Неиспользованные предметы остаются для M04 и финала.
- Последствия питают M05 и Final: питание, вода, повреждение пути, доступ к шлюзу и штраф/бонус времени.

### M04 — «Межвагонная связь»

- Scope: группы вагонов из frozen plan: 2 вагона — одна пара; 3 — одна группа; 4 — две пары 1+3 и 2+4; 5 — группы 1+2 и 3+4+5.
- У каждой группы сервер назначает операторов и лимит сообщений. Instance имеет `interactionPhase: exchange → answer → resolved`: в `exchange` единственный primary CTA — «Передать», после закрытия канала — «Подтвердить ответ»; два действия не конкурируют в первом viewport.
- Отправлять сообщения может только назначенный оператор; `extra_message`, `clarification` и `trade_bonus` открываются сервером в подходящий момент.
- Сделка проходит `proposed → accepted | rejected | expired`; accept атомарно передаёт предмет/улику.
- Группа завершает миссию после согласованного ответа всех вагонов либо явного timeout-assistance outcome.
- Полученные сведения и обмены нужны для M05, M06 и финала.

### M05 — «Один шанс»

- Scope: вагон.
- Команда необратимо выбирает маршрут A или B.
- Исход детерминированно вычисляется из frozen scenario, текущего инвентаря, сохранённых персонажей и реально применённых способностей. Случайности после открытия instance нет.
- `route_analysis`, `terrain_analysis`, `route_feel`, `dangerous_route`, `physical_task` и технические способности становятся ситуационными действиями.
- Исход фиксирует `route_choice`, `route_bonus_minutes`, `track_damage`, `power_instability`, возможный `sector4` artifact и точное списание ресурсов.
- Решение влияет на M06 и длительность/доступные подсказки финала.

### M06 — «Общий протокол»

- Scope: global с wagon-members.
- Каждый вагон получает свой фрагмент и может менять голос до консенсуса или дедлайна.
- Сервер знает правильный маршрут; клиент не получает answer key.
- Успех создаёт глобальные факты `sector=04`, `access_code=4719`, wagon fragments и `coordination_bonus`.
- Timeout не обрывает сюжет: сервер применяет явно отмеченную помощь с меньшим бонусом.
- `SECTOR-04` и `4719` становятся обязательными связями для следующей сцены и финала.

### Сюжетное событие — «Неизвестный пассажир»

- Scope: global, без таймера и без «правильно/неправильно».
- TV кратко зависает, показывает помеху и сообщение о несанкционированном доступе.
- Досье: личность не установлена, билет отсутствует, точка посадки неизвестна, идентификатор `BK-17`.
- Вагоны с уликой M02 видят совпадение и действие «Сравнить данные»; остальные — «Дополнительные сведения отсутствуют».
- Находки: повреждённая служебная карта `…НКЕР`, пропуск уровня 04, схема с сектором 4 и записка с `4719`.
- Восстановление 12% → 37% → 61% → 84% открывает: «Сотрудник технической службы. Объект: Бункер».
- Если в run сохранён персонаж с `bunker_knowledge`, он получает персональное воспоминание и действие «Сообщить команде». После подтверждения TV показывает реальное имя и факт «Сектор 4 — технический вход».
- Фиксируются `unknown_passenger_found`, `bunker_revealed`, `bk17_confirmed`, `sector4_bunker_entry`, `code4719_confirmed`.
- Идемпотентные milestones: `bk17_compared_by_wagon`, `bunker_memory_reported_by_guest`, `recovery_12/37/61/84`, `scene_completed`. Сравнивать может любой гость вагона с entitlement `BK-17`; воспоминание подтверждает только назначенный владелец `bunker_knowledge`.
- M02 failure не блокирует сцену: если entitlement отсутствует, milestone получает outcome `no_prior_match`; sector 4 и 4719 всё равно появляются как находки неизвестного пассажира, но `bk17_confirmed=false`.
- После `recovery_84` сервер запускает 60-секундное окно для доступных персональных действий. Затем instance становится `scene_completed`; переход дальше остаётся ручным. Owner может завершить раньше только `force_outcome` с причиной.
- Сцена заканчивается статусом «Координаты Бункера не установлены» и возвращает свадьбу; она не превращается в отдельную задачу.

### Финал — «30 минут до Бункера»

- Scope: global плюс wagon fragments.
- `final_started_at` — единственный anchor. Frozen plan хранит `finalBaseSeconds=1800`, допустимые M05 bonus sources и пределы `min=-300`, `max=600`. При старте вычисляются и сохраняются `finalBonusSeconds=clamp(sum(route_bonus_minutes)*60,-300,600)` и `finalDurationSeconds=finalBaseSeconds+finalBonusSeconds`: итоговый финал длится от 25 до 40 минут.
- Требуемые параметры: coordinates, sector, access_code, gate_time, password.
- Улики M02/M06/Unknown Passenger и результаты M03/M05 открывают параметры или подсказки; способности `weak_signal`, `bunker_knowledge`, `plan_analysis`, `access_protocol`, `archive_search`, `bunker_systems`, `coordinate_analysis`, `gate_timing` имеют конкретные точки применения.
- `request_access` разрешён только после разрешения всех обязательных параметров.
- Первый валидный запрос атомарно открывает Бункер. Неверная попытка не раскрывает правильные значения и не блокирует продолжение.
- Owner может открыть вручную только отдельной аварийной командой с причиной; это помечается в финальной статистике.
- После открытия показываются итог, вклад вагонов, использованные роли, сохранённые/переданные ресурсы, ошибки, подсказки и owner overrides.

Пять параметров не могут образовать dead end:

| Параметр | Каноническое значение | Основной источник | Обычный fallback | Бонусный источник |
|---|---|---|---|---|
| coordinates | `57°09 / 65°32` | распределённые final fragments | при 12:00 сервер открывает недостающую половину после общего запроса | `coordinate_analysis`, `plan_analysis`, coordination bonus |
| sector | `04` | M05 `SECTOR-4`, M06 consensus или Unknown Passenger | при 10:00 recovered service map | `bunker_knowledge`, `bunker_systems` |
| access_code | `4719` | M06 hidden packet или записка Unknown Passenger | при 08:00 damaged archive показывает все четыре цифры после подтверждения вагонов | `document_analysis`, `archive_search` |
| gate_time | `23:40` | сохранённая связь/питание плюс инженерный анализ | при 06:00 автоматический цикл шлюза в terminal log | `gate_timing`, power/train abilities |
| password | `LV0830` | свадебные материалы и подсказка «LV + дата» | при 04:00 маска `LV_ _ _ _`, при 01:00 дата `0830` | `terminal_hack`, `visual_memory`, `organize_data` |

Значения и нормализация находятся только на сервере. Fallback требует пользовательского подтверждения/ввода, поэтому игра остаётся решаемой без критической роли, но сильный предыдущий путь сохраняет преимущество по времени и числу подсказок.

1. шапка события до 72 px;
2. название до двух строк;
3. полный вопрос до четырёх строк;
4. изображение после вопроса: `height: min(180px, calc((100vw - 32px) * 9 / 16))`, `object-fit: cover`, действие «Развернуть схему»;

## 11. Очередь важных событий

| Приоритет | Примеры | Поведение |
|---|---|---|
| P0 | старт финала, аварийный перехват, исход | один полноэкранный takeover, вытесняет всё |
| P1 | голос, маршрут, расход, подтверждение | модальный лист; следующая P1 ждёт, устаревшая заменяется |
| P2 | предмет, сообщение, способность, подсказка | карточка над контентом с CTA |
| P3 | сохранение, sync, connection | тихий status-toast/журнал |

Автомат очереди:

- P0 немедленно закрывает визуальный UI P1–P3, но не отменяет уже отправленную серверную команду;
- открытая P1 содержит `instanceVersion`; при server-version change она становится read-only итогом «Решение уже принято» или «Время вышло» с CTA «К текущему заданию»;
- P1 заменяется только до подтверждения и только новой версией того же `instance_id`; иначе ждёт очереди;
- P2 объединяются по `(instanceId,eventType)`, P3 не отбирают фокус;
- перед повтором после transport failure клиент перечитывает authoritative state и receipt.

Звук дополняет, но не заменяет текст. Reconnect восстанавливает серверный контекст, а не локальный стек модалей.

## 12. TV-контракт

Основной viewport 1920×1080; дополнительно 1366×768 и 4K. Safe area не меньше 5%.

TV показывает один общий смысловой слой: большой заголовок, серверный таймер, стадия, прогресс 2–5 вагонов или результат. Поля ввода, длинные инструкции и частные данные остаются на телефонах.

Каждая M01–M06, Unknown Passenger и Final имеет отдельную сцену. Никакого схлопывания в `mission_a/mission_b`. Переподключившийся TV сразу показывает текущий кадр и остаток времени, не повторяя уже прошедший звуковой удар.

Сетка вагонов: N=2 — две равные колонки; N=3 — три колонки; N=4 — 2×2; N=5 — 3+2 с центрированным вторым рядом. Всё находится внутри 5% safe area. На 1920×1080 заголовок не меньше 72 px, таймер 112 px, название вагона 28 px; на 1366×768 пропорционально уменьшается, но основной текст не ниже 20 px. TV всегда использует `publicTvSummary`, а не мобильный prompt.

Motion использует существующую свадебную editorial/railway стилистику: окно поезда, архив, бумага, карта, бетон, свет и механика. Красный — только тревога. При `prefers-reduced-motion` blackout/tear/wipe/мигание заменяются мгновенной сменой с текстовым статусом.

Ключевые cues используют реальные локальные записи с pinned hash и attribution. Пространственный звук допустим как микс реальной записи; процедурный генератор не заменяет поезд, gong, дверь, сирену или механическую среду. Перед запуском P0 админ показывает «Звук готов», «Звук выключен» или «Звук не подготовлен»; визуальная сцена остаётся работоспособной без аудио.

Таймер не объявляется screen reader каждую секунду. `aria-live` срабатывает только при старте, 5:00, 1:00, 0:30, 0:10 и 0:00, а также при смене статуса.

- следующее разрешённое действие;
- плановое окно и фактическое время;
- активный таймер;
- число гостей и вагонов;

Опасные действия «Перезапустить таймер», «Остановить Бункер», «Открыть вручную», `force outcome` требуют второго подтверждения, описания эффекта и причины. Каждая команда пишет автора и серверное время.

## 14. Безопасность и приватность

- Прямой доступ `anon/authenticated` к игровым таблицам отозван; RLS включён.
- Клиенты используют узкие `SECURITY DEFINER` RPC с `search_path=''`.
- Guest-команда авторизуется существующим device binding; owner-команда проверяет `events.owner_user_id = auth.uid()`.
- Hidden trait, правильные ответы, чужие private hints и нераскрытые фрагменты не сериализуются.
- Event payload не хранит device key, plaintext правильного ответа или финальный пароль.
- TV получает только публичную агрегированную read-модель без персональных секретов.
- Ведущий получает диагностическую read-модель и неизменяемый аудит.

## 15. Realtime, ошибки и восстановление

Realtime несёт только refresh-сигнал. После него телефон, TV и админка перечитывают authoritative read-модель. Polling/focus/online fallback остаётся обязательным.

RPC-успех остаётся успехом даже при сбое broadcast. При неоднозначной transport-ошибке клиент сначала перечитывает серверное состояние и только затем предлагает повтор. Это исключает двойной расход, повторный старт таймера и повторную передачу.

Офлайн-клиент не получает локальное право выполнить просроченное действие. После reconnect он видит серверный итог и CTA к текущему заданию.

## 16. Reset и режим тестирования

`Сбросить игровой прогресс` очищает V2 run, instances, decisions, receipts, transfers, final parameters и event log, но сохраняет `guests`, device bindings, вагоны и свадебные анкеты. Полный репетиционный reset остаётся отдельной опасной операцией.

Test Mode доступен только owner:

- создаёт N синтетических гостей с пометкой `is_test=true`;
- распределяет их по фактическому алгоритму;
- может seed-детерминированно выбирать успешные и ошибочные решения;
- ускоряет только тестовые дедлайны;
- прогоняет M01–Final и проверяет инварианты;
- удаляет только тестовые данные по `test_run_id`;
- никогда не использует production device keys и не отправляет внешние уведомления.

## 17. Переход со старого слоя

1. Добавить `contract_version=2` и V2-проекции forward-only миграцией.
2. Новый prepare создаёт только V2 run и frozen instances.
3. Старый активный run продолжает обслуживаться старым read path до stop/reset.
4. V2 read-модели ветвятся по `contract_version` и не читают `bunker_team_progress` как источник M01–M06.
5. V2 не делает dual-write в `mission_a/mission_b` и старый numeric final code.
6. После завершения production rehearsal legacy UI/RPC помечаются deprecated; таблицы удаляются только отдельной поздней миграцией.
7. Wedding registration, Quiz, MK, Premiere, screen events и train arrival не меняют контракты.

## 18. Проверка и release gate

### Контрактные тесты

- полный fixture 36 персонажей: key, профессия, здоровье, навык, скрытое свойство, ability id, полный текст эффекта и точные теги;
- parity/hash всех нормативных полей канона DB↔TS;
- controlled random для каждого N=15…40 с проверкой каждого минимума категорий;
- каждая assignment ссылается только на один из 36 ключей и не создаёт имя/роль/свойство/способность;
- для N=30–35 `distinctProfileCount=N`, для 36 — 36, для 37–40 — 36 и число повторных выдач N−36; частота каждого ключа ≤2;
- повтор одного profile key разводится по разным вагонам, когда существует допустимая раскладка;
- сокрытие hidden trait и отсутствие rarity;
- имя берётся из регистрации, а каталог не содержит поля имени;
- атомарное применение каждой способности;
- M01 quota, M04 grouping, M06 fragments, Final parameters для 2–5 вагонов;
- идемпотентность всех команд и конфликт request hash;
- запрет отрицательного инвентаря и двойного расхода/обмена;
- RLS, revoke/grant, owner/device authorization и пустой search path.

### Сценарные тесты

- N: 15, 16, 17, 23, 32, 39, 40;
- поздний гость на каждой ключевой стадии;
- reload телефона и TV на каждой стадии;
- одновременный расход последнего предмета;
- одновременный accept одной сделки;
- потеря Realtime и восстановление polling/focus/online;
- `excluded` персонаж продолжает играть;
- финалы с разным инвентарём, маршрутами и подсказками;
- reset сохраняет свадебные анкеты;
- random seeded end-to-end для каждого N=15…40.

### Визуальный gate

- 320×844, 390×844, 430×932, 844×390;
- 1366×768, 1920×1080, 3840×2160;
- reduced motion, звук выключен, клавиатура и screen reader;
- вопрос и CTA в первом viewport при иллюстрации и длинном реальном имени;
- 2–5 вагонов в safe area;
- только русские понятные названия, без raw enum/item key;
- настоящие растровые ассеты/иконки; без emoji, CSS-art, inline SVG и заглушек.

### Итоговый release gate

1. Focused Vitest/pgTAP на каждом пакете.
2. Полный Vitest, typecheck, production build и diff check.
3. Реальное выполнение всех forward migrations.
4. Rollback-only authenticated и guest/device probes.
5. Supabase advisors без новых ошибок.
6. Playwright полного owner/phone/TV сценария.
7. Production-like rehearsal с тестовыми гостями и очисткой `test_run_id`.

## 19. Декомпозиция реализации

Из-за размера система реализуется шестью согласованными пакетами, каждый с TDD и независимым review:

1. **V2 contracts** — канонический пул, plan snapshot, instances, commands, receipts, events, legacy boundary.
2. **M01–M02** — выбор персонажей, reveal, способности, Black Box и `BK-17`.
3. **M03–M04** — inventory ledger, капитан, resource decisions, сообщения и сделки.
4. **M05–M06** — маршруты, последствия, консенсус, `SECTOR-04`, `4719`.
5. **Unknown Passenger + Final** — сюжетный reveal, пять параметров, таймер, outcome и статистика.
6. **Experience + verification** — телефон, TV, админ-таймлайн, ассеты/звук, Test Mode и полный rehearsal.

Пакеты 2–6 не начинают менять production-контракт до завершения пакета 1. После каждой схемной миграции выполняется security review; после каждого пользовательского пакета — visual/UX review.

## 20. Не входит в V2

- вымышленные имена гостей;
- предатель, заражённый или реальное исключение игрока;
- рейтинг персонажей и leaderboard;
- AI-оценка свободного текста;
- нативные push/SMS/Telegram при закрытом сайте;
- автоматический запуск этапов по расписанию;
- изменение свадебной регистрации, билета, MK, Quiz или Premiere вне интеграции приоритетов.
