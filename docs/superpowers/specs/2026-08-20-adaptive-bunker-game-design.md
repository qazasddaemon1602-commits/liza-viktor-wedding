# «Бункер / Последний вагон» — архитектурная спецификация

Дата: 20 августа 2026
Статус: утверждено пользователем

## Цель

Расширить существующий свадебный сайт полноценной игрой для 12–45 участников, не создавая второго приложения и не дублируя регистрацию, вагоны, TV, realtime, админку и механизм репетиционного сброса.

## Переиспользуемые источники истины

- `events` и `event_state` — свадьба и текущий экран;
- `guests` — настоящее имя, регистрация и устройство гостя;
- `carriages` и `guests.carriage_id` — единственная модель вагонов;
- `bunker_state.run_nonce` — идентификатор текущей игровой сессии;
- существующий канал `bunker:{eventSlug}` — refresh-only realtime;
- `BunkerScreenGuard` — высший приоритет Bunker на TV;
- существующая owner-админка — единственная панель ведущего;
- `owner_reset_event_test_data` — полный репетиционный сброс без удаления ответов пары.

Игровые таблицы не копируют имя гостя или номер вагона. Они хранят внешние ключи на `guests` и `carriages` и всегда читают актуальное настоящее имя через существующего гостя.

## Сессия и состояния

`bunker_state` остаётся серверным состоянием текущей сессии. К нему добавляется `global_game_state`:

`LOBBY → CHARACTERS_READY → MISSION_01 → BREAK → MISSION_02 → MISSION_03 → MISSION_04 → MISSION_05 → MISSION_06 → STORY_BUNKER → BREAK_BEFORE_FINAL → FINAL_30 → BUNKER_OPEN → FINISHED`.

Переходы выполняются только owner RPC. Realtime передаёт только сигнал перечитать состояние. Финальный таймер вычисляется от серверных `final_started_at` и `final_duration`; браузеры не создают независимый countdown.

## Персонажи

Конфигурационный пул содержит ровно предоставленные пользователем 36 профилей. Профиль хранит профессию, здоровье, открытый навык, скрытую характеристику, одну специальную способность и теги. Имя не входит в профиль.

Выданный персонаж хранится в `bunker_guest_profiles` с уникальностью `(run_nonce, guest_id)`. Он не меняется после выдачи. `character_status` относится к сюжетному персонажу (`active | saved | excluded`), но гость всегда продолжает играть.

Controlled random сначала закрывает обязательные группы: technical, medical, information, communication, bunker knowledge, navigation. Для 15–20 гостей применяются целевые квоты из пользовательской спецификации. Остальные профили выбираются воспроизводимо по `run_nonce`, без показа силы или редкости. Одна роль получает одну способность, доступную не более заданного числа использований.

## Вагонная модель

Количество активных вагонов определяется существующим распределителем: 2 для 12–18, 3 для 19–26, 4 для 27–36, 5 для 37–45. Ведущий может выбрать 2–5 с предупреждением о маленьких командах. Подтверждение атомарно перераспределяет текущих гостей и фиксирует состав; поздний гость попадает в наименее заполненный активный вагон без перемешивания остальных.

`bunker_wagon_state` хранит только runtime-поля вагона. Инвентарь, архив, миссии, сообщения и сделки ссылаются на существующий `carriage_id`.

## Данные PHASE 2

- `bunker_character_profiles` — неизменяемая конфигурация 36 ролей;
- расширенный `bunker_guest_profiles` — роль гостя в конкретном run;
- `bunker_wagon_state` — питание, связь, навигация, дверь, повреждения, вода, маршрут;
- `bunker_inventory_lots` — количества предметов и их жизненный цикл;
- `bunker_archive_entries` — текст, изображение, карта, аудио, документ и код;
- `bunker_game_events` — append-only-ish журнал для восстановления и статистики;
- `bunker_game_runs.plan` — зафиксированный масштаб Mission 01/04/06 и финала.

Все игровые таблицы в `public` используют RLS, но прямой доступ `anon/authenticated` отозван. Клиенты работают только через минимальные `security definer` RPC с явной проверкой guest device binding или владельца события.

## Атомарность

Расход предметов, использование способности, сделка, голос и открытие Бункера блокируют соответствующую строку `FOR UPDATE` и записывают событие в той же транзакции. Повторный запрос должен быть идемпотентным либо возвращать уже достигнутое состояние. Количество предмета никогда не становится отрицательным.

## Late registration

Регистрация остаётся доступной во время игры. При первом чтении Bunker-state позднему гостю атомарно создаётся персонаж текущего run, а уже принятые решения вагона не меняются. Ответ содержит `joinedLate: true`, если гость зарегистрирован после начала сессии, и UI показывает утверждённое сообщение.

## Reset

`СБРОСИТЬ ИГРОВОЙ ПРОГРЕСС` удаляет runtime игры, но сохраняет `guests`, device bindings и свадебные анкеты. Существующий репетиционный сброс может дополнительно удалить регистрации. Полный reset остаётся отдельной опасной owner-операцией с вводом `RESET`.

## Последующие фазы

Player dashboard, owner dashboard и TV читают одну серверную модель. Миссии добавляются последовательно поверх неё. Ни одна миссия не определяет поведение через фиксированные `wagon_1 ... wagon_4`; входами являются active wagon ids, размеры команд и сохранённое состояние текущего run.
